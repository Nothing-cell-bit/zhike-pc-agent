# 接待执行与演示报价验收

本轮目标是让已有需求驱动实际回答、比较和条件报价，避免所有事项一起停在“待核实”。客户和客服均使用真实模型调用：客户模型只看到画像及实际问答；客服由生产入口 `backend.ai.analysis → service_workflow.run` 生成。模拟脚本逐轮原样采用第一条有效建议，通过网站相同的发送校验写入隔离数据库。

## 五项修复

| 原因 | 修复 | 验证方式 |
| --- | --- | --- |
| 进度复核只能返回追问，没有可执行工作出口 | 从带客户原话的requests生成业务任务，ready_work可执行回答、比较、推荐或报价 | 真实对话的request_dispatch与ready_work_dispatch记录；条件询价回归 |
| 检索片段变动导致已知参数被说成未知 | 保留本轮source_pool；按产品和请求字段构造原文表；幂等分段 | 多产品重量、分辨率、色域覆盖；CPU短值及操作系统字段校验 |
| 只展示机型名称就把比较记为完成 | 参数表覆盖及实际发送后才完成；缺失项保留门店待办 | 草稿状态与实际发送后的状态对比 |
| 性能和价格问题合并等待，报价未生成 | 单独准入quote请求，先由规则准备价格，再写话术；待审批L4不阻断有效L1–L3 | 原Fold画像实际生成报价卡，性能任务仍待核实 |
| 确认已有约定被误判为新进展，反复承诺 | confirm不计新事实；无独立工作时不重复生成；相同推荐表不重复交付 | 确认约定不调用表达器；同表不重复推荐回归 |

真实模型重跑还发现并修复了产品ID误作销售配置ID导致空报价的问题。程序丢弃无效ID，按已有目录准备有效选项；报价动作不能没有销售配置。所有变更均为通用状态与证据规则，没有针对某轮客户原话硬编码客服答案。

逐轮复核还修复了三处边界：含问号的引文应按原文位置定位上下文，不能引入另一句“会不会卡顿”的否定词而丢弃询价；CPU字段不能取显卡脚注里提到处理器的文字，色域应保留Windows和Linux两个版本；已批准规则中的配置说明必须经过真实销售选项匹配并保留到发送卡片，不能把Ultra 7报价当Ultra 9报价。没有匹配的授权配置时保留具体门店待办。内部“已发送”只根据实际报价卡的等级记录，不能把未批准的L4连带标为已发送。

## 演示数据边界

用户明确授权本次模拟生成测试价格。`scripts/demo_price_fixture.py` 仅允许向 `dialogue-natural-*` 隔离库写入，并拒绝正式data目录。知识库索引复制到隔离目录，仅在副本中加入两个X Pro虚构销售SKU；产品事实原文保持不变。L1演示15999元；L2演示减500元；L3演示电脑加鼠标16298元；L4保留未审批。前台文字、报价卡和问答Markdown均标注演示。虚构销售组合不能视为真实在售SKU。

模拟没有登记任何虚构的游戏实测、Excel负载或软件兼容结论。价格卡成功表示报价路径可执行，不表示候选已满足全部性能条件，也不表示客户已购买。正式数据库仍无真实报价规则，不能把演示金额用于真实销售。
