# 统一接待链路：service-v8

整体设计见 [客服多轮 AI 接待总体规划](design/customer-service-master-plan.md)。本文说明需求主线、资料检索、任务推进、人工核实和规则报价如何衔接。

当前生产入口是 backend.ai.analysis → service_workflow.run；dialogue.run 保留旧领域协议兼容测试，不再作为当前接待入口。

## 主线、当前主题与个人需求

mission 是持续服务目标；topic 是客户这一轮正在问的问题；needs 保存实际使用者、购机意向、预算、活动、必用软件、顾虑和已同意的后续约定。插入参数问题不覆盖主线。未谈的信息保持未知，真实购机动作不复用作客户身份，当前的选配置/询价指令不记为后续约定。

模型提交增量并引用客户原话。程序校验消息角色、原文、范围、人工锁定和事实时序；旧消息不能覆盖较新的预算或已锁定字段。初次整理读取历史；后续以状态和未处理消息为主，保留最近对话用于解析指代。未发送的候选不算已问，改掉的问句也不登记。

## 执行顺序与权限

| 阶段 | 模型负责 | 程序负责 |
| --- | --- | --- |
| ServicePlanning | 理解当前意图、需求增量、主线和下一项工作 | 准入原话、锁定和时序；限定任务类别与权限 |
| 资料与工具 | 选择待查产品 | 查技术事实/候选；按授权规则核价；保留版本脚注 |
| ServiceDraft | 三条自然表达，可提出相关客户环境信息请求 | 验证是否未知、已问、拒答、委托或受范围限制；安排允许的可选探索 |
| ServiceAudit | 每条候选分别判定事实依据与本轮相关性，报告无效需求字段 | 缺少单条判定也拒收；只接受否决，不让审核器制造新事实、任务或价格 |
| 保存与发送 | 无自动发送权限 | 检查修订号、消息版本、锁定和状态；发送前重新核价并生成报价卡 |

客户新消息的普通路径为需求提取、规划、表达、核验；确认待核实事项且无新进展时，省略表达和核验，保持会话开启并等待门店。结构化输出使用已配置模型服务器的 JSON Schema 约束，防止把任务状态快照或输入字段重复输出。提示用 schema 压缩只移除 schema 注释，不得误删业务 properties 中的 title 等同名字段。

审核只依据真实对话判定客户本轮请求，不把规划器的 topic.request 当成客户提出的新问题。沟通范围限制可选转题时，由程序直接收回 bridge，避免仅为此重新生成整份计划。审核不会因“请提供信息”要求模型在缺少资料时证明性能或兼容性。

表达器只选择本次证据编号；程序补回原始段落，避免模型复抄、拼接或改写引文。短编号只在单次调用内使用，保存的是原资料 ID 和原文。选型资料按产品与段落分开，配置条件和相邻脚注保留。历史参考价不作为预算适配或正式门店价依据。

## 对话推进与业务任务

`next_question` 是下一项客户信息请求的单一来源。程序将它编译为采集任务，必要追问直接复用该问题，可选推进则允许不追问的候选。每次客户提供信息后都重新评估推进机会，不依赖客户额外确认。`service_state.synchronize_progress` 根据已准入事实与实际问答同步问题及任务状态，保留简短回答的提问语境。

规划输入不包含上次的 continuation、planned_question 或模型生成的 topic.request；真实对话、已准入需求和实际任务状态才是重新决策的依据。旧的未发送任务只是建议，不能反过来当成客户需求。

确认收到不等于结束。局部聚焦在客户确认该答复后释放；整场范围需客户明确撤回。任务等待与是否要回复是两个状态：等待门店核实不妨碍回应新客户消息，也不阻塞独立的客户信息采集。普通参数咨询不带报价流程，回答完可不追问。

任务区分 answer、discover、recommend、compare、quote、verify。discover 只采集客户字段或其独立未知细节；兼容结论、门店价格及库存属于店内事实核实。任务有稳定 key、归属、依赖、状态和完成条件。模型只能提计划或引用已有任务，不能写入完成状态、人工核实结果或实际发送记录。

生成草稿不完成任务。真正发送对应答复、收到客户有效回答、发送有效推荐/报价卡或客服登记结果才推进对应状态。大幅编辑答复后保守保留待办，避免把无关消息误判成已解答。

比较与参数交付要求覆盖请求的产品、字段和实际发送的来源表；仅列产品名称不算比较完成。检索保留完整的本轮证据池，按产品覆盖所需字段，不以表达器选用的少量片段代替资料是否存在。操作系统字段不能从屏幕段落的“Windows版刷新率”推得。已发送且内容未变的推荐表不重复当作新进展；现有目录没有确认满足硬性要求的候选时，说明资料边界，不承诺自动继续筛选。

仅确认已有跟进约定的confirm增量不算新的待交付工作。遇到客户真正询价，先校验销售配置ID；模型误用产品ID时，拒绝该ID并从实际目录重新准备有效候选，不能保存无配置、无报价的空quote动作。经复核的价格规则可携带configuration_label说明它授权的销售组合；其金额、SKU、期限及配置说明均来自规则，不由话术模型拼写。客户未确认具体组合时，价格说明不等于客户已选定或实测适配。

登记核实结果产生待消费事件。即使没有新客户消息，也继续处理其结果；失败或旧结果被拒绝时不丢事件。价格规则、资格和有效期变化通过核价签名识别，同样可恢复既有报价任务。界面只显示具体目标、待办、结果操作和候选，不显示证据链、模型推导或内部编号。

## 可用候选与有界纠错

非必要澄清保留不追问的选择；有用的探索由上下文和任务决定，不固定问卷顺序。阻塞问题才需要每条候选都保留对应问题。模型不得通过更换 topic_key 绕过已知字段保护。

逐条核验候选，保留通过的表达。已有1至3条可用回复且满足必要澄清、沟通范围及接话约束时直接展示，不为凑三个候选继续调用模型。确需修正时仍有界重试并锁定方案上下文，不能重新选择价格或配置；没有任何合格回复时报告失败并保留旧记录，不用空白或固定问题冒充成功。

## 证据边界

补充候选采用已经通过审核的答复作为事实边界，仅改表达和允许的问题，不重新开放全部产品资料与选型。已有正确候选保留，重复候选明确反馈并拒收。候选数量记录实际核验通过的条数，不能把原始草稿或重复表达计入成功结果。

正面能力列表不能证明其他能力不存在。对“不支持、不能、没有、全系、唯一”等否定或穷尽表述，程序要求引用包含对应明确谓词；“未列明、不能确认”和 A不A 疑问表达不视为否定事实。仅支持对外供电不证明不能向电脑充电；只列一种容量也不证明无其他容量。这是跨产品的证据规则，不靠具体型号或问法补丁。

程序约束不替代语义核验：仍需检查来源与型号、版本、限定条件及实际命题是否一致。候选由客服确认后发送。

## 验证与性能

运行 scripts/evaluate_service_workflow.py --live，在隔离数据库保存多产品多轮的原话、候选、采用记录、需求、任务、源码散列和真实调用耗时。必须逐句人工复核，自动检查通过不等于语义正确；早期接口充电的错误否定已保留在失败记录中，不能当成正确验收样本。

生产路径测试位于 tests/test_service_workflow.py、test_structured_service_output.py。旧 v4 fixtures 显式调用 legacy_analysis，不能替代新生产链路验收。实际验证范围见 [作品说明书](competition/WORK_DESCRIPTION.md)；轻量连接测试耗时不是完整回复耗时。不承诺所有对话均达到 3–5 秒。
